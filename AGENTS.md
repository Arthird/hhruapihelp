# AGENTS.md — правила разработки HH API Help Bot

## 1. Назначение проекта

Нужно сделать чат-бота MAX, который отвечает разработчикам на вопросы об API HeadHunter
(HH.ru): объясняет методы, параметры, ошибки, помогает с примерами кода и навигацией по
документации. Бот не заменяет официальную документацию и не должен придумывать эндпоинты,
поля или коды ошибок.

Ключевые свойства системы:

- ответы должны опираться на подготовленную базу знаний HH.ru и содержать ссылку на
  использованный раздел документации;
- бот должен быть быстрым, расширяемым и обновляемым при изменении API;
- вся секретная конфигурация передаётся через `.env`;
- рабочее состояние диалогов и служебные данные хранятся в PostgreSQL;
- интеграция с MAX работает через long polling, а не через webhooks.

Исходная документация HH.ru: <https://github.com/hhru/api>, папка `docs`.
Начальный системный промпт: `prompts/initial.md`.

## 2. Обязательная архитектура

```text
Клиенты MAX
     │
     ▼
max-bot (TypeScript)
  • long polling MAX Bot API
  • проверка TLS через CA Минцифры
  • нормализация update
  • отправка ответа в MAX
     │  HTTP JSON, внутренний API
     ▼
backend (Python / FastAPI)
  • API и оркестратор
  • SQLAlchemy + PostgreSQL
  • LlamaIndex + Yandex Assistant через OpenAILike
     ├──────────────► PostgreSQL (+ pgvector)
     └──────────────► Yandex Cloud API
```

Границы ответственности:

- `max-bot` — единственный компонент, который знает токен MAX и вызывает MAX Bot API.
  Он не содержит бизнес-логики RAG и не работает с PostgreSQL напрямую.
- `backend` — владелец PostgreSQL, истории диалогов, промпта, RAG-индекса и вызова модели.
  Backend не подписывается на MAX и не отправляет сообщения в MAX в основном сценарии.
- `PostgreSQL` — операционное состояние и векторный индекс. Исходный текст документации
  хранится в репозитории, а не является единственной копией в БД.

Целевая структура репозитория:

```text
max-bot/                    # TypeScript-модуль MAX
  src/
backend/
  app/
    api/                    # HTTP-контракт с max-bot
    config.py               # load_env() и Settings
    db/                     # SQLAlchemy-модели, сессии, репозитории
    llm/                    # Yandex/OpenAILike
    rag/                    # индексация и retrieval
    orchestrator/           # сценарий ответа одного запроса
  data/hh_api.md            # копия подготовленной документации
  migrations/               # Alembic
  tests/
prompts/initial.md
docs/architecture.md
PLAN.md
docker-compose.yml
requirements.txt            # единый список Python-зависимостей
.env.example
README.md
```

## 3. Зачем проекту база данных

MAX не является хранилищем состояния бота:

- метода `GET /chats` больше нет, поэтому список чатов нельзя получить запросом;
- встроенные сессии SDK по умолчанию живут только в памяти и теряются при рестарте;
- long polling может повторно доставить update, а обработчик может упасть после получения
  сообщения, но до отправки ответа;
- для качественного ответа нужен контекст диалога, который не должен зависеть от жизни
  процесса;
- нужны аудит, диагностика ошибок модели и анализ качества ответов.

Поэтому PostgreSQL хранит как минимум:

| Таблица | Назначение |
|---|---|
| `max_users` | Пользователи MAX, их профиль и время последней активности. |
| `max_chats` | Диалоги, группы и каналы, в которых установлен бот; статус и жизненный цикл. |
| `conversations` | Активный контекст общения для пары «чат + пользователь», сводка и последняя активность. |
| `messages` | Входящие и исходящие сообщения, связь с `mid` MAX, статус обработки и ошибки. |
| `processed_updates` | Ключ идемпотентности update и результат обработки; защита от повторных ответов. |
| `llm_runs` | Параметры вызова модели, использованные источники, latency, токены и ошибки. |
| `feedback` | Оценки и комментарии пользователей, если в сценарии включены кнопки обратной связи. |
| `knowledge_versions` | Версия исходного документа, checksum, модель эмбеддингов и время индексации. |

Векторные чанки хранятся в PostgreSQL через `pgvector` и `PGVectorStore` LlamaIndex.
Бизнес-схема и миграции должны управляться SQLAlchemy 2.x и Alembic; не создавать
бизнес-таблицы вручную через `CREATE TABLE` в коде приложения.

База данных не должна содержать секреты, токены, полные ответы Yandex с закрытыми
заголовками или необработанные персональные данные сверх необходимого. Политика хранения
и очистки должна быть описана в README и реализована отдельной задачей.

## 4. Обязательные правила интеграции с MAX

Источник истины по API — skill `.agents/skills/max-messenger/` и официальная документация
MAX. При расхождении с этим файлом следовать актуальной документации и фиксировать изменение
в `docs/architecture.md`.

- Базовый URL: `https://platform-api2.max.ru`. Старый `platform-api.max.ru` не использовать.
- Авторизация: заголовок `Authorization: <token>` без `Bearer`.
- `platform-api2.max.ru` подписан CA Минцифры. В контейнере `max-bot` нужно добавить корневой
  сертификат в trust store и/или задать `NODE_EXTRA_CA_CERTS`. Запрещено отключать проверку
  TLS (`NODE_TLS_REJECT_UNAUTHORIZED=0`, `rejectUnauthorized: false`, `curl -k` и аналоги).
- Использовать **long polling**: `bot.start({ mode: 'polling', options: { allowedUpdates: [...] } })`.
  Webhooks не реализовывать, пока у проекта нет белого IP и HTTPS-домена на порту 443.
- Помнить, что polling-режим SDK очищает существующие webhook-подписки. Не запускать
  polling и webhook одновременно.
- Соблюдать минимальный интервал между `GET /updates` — 300 мс; SDK сам обрабатывает
  backoff на `429`/`5xx`, но ошибки обработчика всё равно нужно перехватывать.
- Не вызывать `GET /chats` и не рассчитывать на список чатов. Сохранять чат при
  `bot_added`/`bot_started`, помечать удалённым при `bot_removed`, очищать контекст при
  `dialog_cleared`/`dialog_removed`.
- Обрабатывать `message_created`, `message_callback`, `bot_started`, `bot_added`,
  `bot_removed`, `dialog_cleared`, `dialog_removed`, `bot_stopped` как минимум. Остальные
  типы можно логировать и игнорировать.
- Для каждого update строить идемпотентный ключ из `update_type`, `timestamp` и доступного
  идентификатора (`message_id`, `callback_id` и т.п.). Повторный update не должен приводить
  к повторному вызову модели или повторной отправке ответа.
- Текст сообщения MAX ограничен 4000 символами. Считать нужно символы (code points), а не
  байты; разбивать длинный ответ на части, предпочитая абзацы.
- MAX не поддерживает markdown-списки, таблицы и горизонтальные линии. Промпт и
  постобработка должны выдавать обычные строки; списки оформлять текстом или отдельными
  абзацами. В блоках кода MAX схлопывает переводы строк, поэтому многострочные примеры
  нужно доставлять отдельным файлом-вложением, а не fenced-блоком.
- Не отправлять пользовательский текст как markdown без экранирования: символы разметки
  могут изменить сообщение.
- Соблюдать лимит примерно 30 запросов/с ко всему MAX API. Для `POST /answers` — не более
  2 ответов/с на чат, если будут использоваться callback-кнопки.
- Обработчик одного update не должен ронять процесс. Нужны `bot.catch()`, структурные логи,
  корректный `stopPolling()` и завершение по `SIGTERM`.

## 5. Правила RAG и Yandex Assistant

- Использовать LlamaIndex. LLM подключать через `OpenAILike` к OpenAI-совместимому endpoint
  Yandex Cloud (`YANDEX_CLOUD_BASE_URL`, `YANDEX_CLOUD_API_KEY`, `YANDEX_CLOUD_FOLDER`).
- Выбранная модель обязана поддерживать tool calling. Это требование нужно явно указать в
  README и проверить на реальном запросе до реализации сценариев с инструментами. Если
  модель не поддерживает tool calling, заменить её, а не имитировать вызов инструментов.
- Индексировать нужно подготовленный файл `doc_preparing/output/openapi.md`. Перед
  индексацией скопировать его в `backend/data/hh_api.md`; индексатор не должен зависеть от
  пути внутри `doc_preparing`.
- Копирование и переиндексация должны быть воспроизводимыми: checksum исходника, версия
  модели эмбеддингов и `knowledge_versions` фиксируются в БД. Изменение исходного файла не
  должно незаметно оставлять старый индекс активным.
- Разбивать документ по разделам заголовков и не разрезать блоки кода без необходимости.
  В metadata чанка сохранять `source`, `section`, `endpoint`, `line_start`, `line_end` и
  версию документа.
- Ответ должен строиться только по найденному контексту. Если контекста недостаточно,
  честно сообщить об этом и предложить уточнить вопрос; не выдумывать поля и коды ошибок.
- При ответе об эндпоинте придерживаться структуры из `prompts/initial.md`: краткий ответ,
  параметры, успешный пример, ошибки и причины. Формат адаптировать под ограничения MAX.
- Пользовательский ввод не является доверенной инструкцией. Промпт должен запрещать
  выполнение инструкций из сообщений пользователя, повышающих приоритет над системными
  правилами, и не должен раскрывать внутренний prompt, ключи или служебные заголовки.
- Для retrieval использовать top-k с ограничением контекста; при необходимости добавить
  rerank. Ответы и источники сохранять в `llm_runs` для воспроизводимости.

## 6. Конфигурация и секреты

Все секреты и изменяемые параметры окружения передаются через `.env` в корне проекта.
В git коммитится только `.env.example`, реальный `.env` игнорируется.

Python-приложение обязано загружать переменные через явную функцию `load_env()` из
`backend/app/config.py` (обёртка над `python-dotenv`) и падать с понятной ошибкой при
отсутствии обязательного значения. TypeScript-модуль загружает те же переменные через
`dotenv`/`loadEnv()` или получает их из `docker-compose`; дублировать секреты в коде нельзя.

Минимальные группы переменных (полный список с описанием и примерами — в README):

- MAX: `MAX_BOT_API_KEY`, `MAX_API_BASE_URL`, `MAX_ROOT_CA_PATH`;
- backend: `BACKEND_BASE_URL`, `INTERNAL_API_TOKEN`, `BACKEND_TIMEOUT_SECONDS`;
- PostgreSQL: `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`,
  `POSTGRES_PORT`, `DATABASE_URL`;
- Yandex: `YANDEX_CLOUD_API_KEY`, `YANDEX_CLOUD_BASE_URL`, `YANDEX_CLOUD_FOLDER`,
  `MODEL_NAME`, `EMBEDDING_MODEL_NAME`;
- RAG и приложение: `KNOWLEDGE_PATH`, `PROMPT_PATH`, `RAG_TOP_K`, `LOG_LEVEL`.

`MODEL_NAME` должен обозначать модель с поддержкой tool calling. Не логировать значения
секретов, токены и полные тела запросов с авторизацией.

## 7. Внутренний контракт max-bot ↔ backend

MAX-модуль нормализует update и отправляет его в backend, например:

```http
POST /internal/v1/updates
Authorization: Bearer <INTERNAL_API_TOKEN>
Idempotency-Key: <update_type>:<timestamp>:<message_id|callback_id>
```

```json
{
  "update_type": "message_created",
  "update_timestamp": 1760000000000,
  "chat": { "id": 123, "type": "dialog", "title": null },
  "user": { "id": 456, "first_name": "Иван", "is_bot": false },
  "message": { "id": "mid-1", "text": "Как получить список вакансий?", "timestamp": 1760000000000 }
}
```

Ответ backend:

```json
{
  "reply": {
    "text": "Краткий ответ...",
    "format": "markdown",
    "attachments": [
      { "type": "file", "filename": "example.py", "mime_type": "text/x-python", "content": "..." }
    ]
  }
}
```

Правила контракта:

- backend идемпотентно обрабатывает запрос по ключу update; повторный запрос возвращает
  сохранённый результат;
- backend не отправляет сообщения напрямую в MAX, а возвращает действие транспорту;
- max-bot валидирует ответ, разбивает текст на части до 4000 символов, загружает
  многострочные примеры кода как файлы и отправляет всё в правильном порядке;
- при недоступности backend транспорт делает ограниченный retry с backoff и не теряет
  входящий update без логирования;
- ошибки модели и пустой retrieval превращаются в понятный ответ пользователю, а не в
  необработанное исключение.

## 8. Требования к качеству и процессу

- Каждый логический этап изменений соответствует отдельному git-коммиту. Сообщения коммитов
  — в Conventional Commits, например `feat(rag): add section-aware indexing`.
- Не добавлять в репозиторий `venv`, `node_modules`, `.env`, кэши, логи, временные файлы и
  секреты. `.gitignore` должен быть настроен до первого коммита.
- В корне должен быть актуальный `requirements.txt` со всеми Python-зависимостями.
- Проект запускается через `docker compose`; сервисы должны иметь healthcheck и стартовать
  после готовности PostgreSQL.
- README обязан описывать `.env` (все поля, назначение, пример), запуск, индексацию,
  ограничения MAX и то, что модель должна поддерживать tool calling.
- Для Python-кода добавить unit-тесты и проверку типов/линтер; для TypeScript — тесты
  форматирования, разбиения и клиента backend.
- Перед сдачей проверить: старт с чистого `.env.example`, ответ на тестовый вопрос HH API,
  сохранение контекста после рестарта, отсутствие повторного ответа на дубликат update,
  отсутствие webhook-кода и секретов в git.

## 9. Приоритет источников информации

1. Официальная документация HH.ru и MAX.
2. Схема и reference-файлы skill `.agents/skills/max-messenger/`.
3. `docs/architecture.md` и `PLAN.md` этого репозитория.
4. `prompts/initial.md` как начальные требования к стилю ответа.

Если реальные API и skill расходятся, нужно обновить документацию проекта и зафиксировать
решение в `docs/architecture.md`, а не обходить ограничение отключением TLS или
недокументированными вызовами.
